# Шаблон наряда для coding agent

Замени `<TASK_ID>` на ID задачи и отдай агенту целиком. Больше ничего править не нужно.

```
Работай по `D:\dev\HydraBox\hydrabox\docs\HYDRABOX_RUNTIME_IMPLEMENTATION_PLAN.md`.

Задача: <TASK_ID>

## ЧТО ПРОЧИТАТЬ ДО НАЧАЛА
1. §0 AGENT EXECUTION CONTRACT — целиком.
2. Карточку <TASK_ID> в §4 — целиком, включая DO NOT CHANGE и STOP CONDITIONS.
3. Инварианты из её INVARIANTS ESTABLISHED по §2.1 и упомянутые в карточке контракты §2.2-2.11.

## PRECONDITIONS: ПРОВЕРЯТЬ ПО КОДУ, НЕ ПО ДОКУМЕНТУ
Поле STATUS в §4 и в таблице §7 рассчитано от состояния «ничего не выполнено» и по ходу
исполнения плана НЕ обновляется. Само по себе `BLOCKED(...)` признаком блокировки не является.

Фактическую готовность определяй так:
- `git log --oneline -15` в репозитории задачи (hydrabox: `D:\dev\HydraBox\hydrabox`,
  hydracore: `D:\dev\hydracore\hydracore`);
- прогони NEGATIVE ASSERTIONS тех карточек, что перечислены в PRECONDITIONS.

Порядок проверки:
1. `docs/TASK_LEDGER.md` — журнал исполнения. Ищи строку каждой задачи из PRECONDITIONS.
   `DONE` в журнале = предшественник выполнен, точка.
2. Если строки нет — `git log --grep="Task: <ID>"` в нужном репозитории.
3. Если и там нет — сопоставь по смыслу карточки, коммиты старше журнала ID не содержат.

NEGATIVE ASSERTIONS предшественника читаются в границах ЕГО FILES / SYMBOLS, а не по
всему файлу или репозиторию. Ненулевой grep вне этих границ — ожидаемое состояние, а не
признак незавершённой задачи: остатки снимаются позже другими задачами.

Дальше:
- предшественник виден в git log либо его NEGATIVE ASSERTIONS уже дают ноль → задача READY, работай;
- предшественника нет → `RESULT: BLOCKED`, укажи, какие коммиты и грепы проверил;
- карточка ждёт `HB-EXP-*` → `RESULT: BLOCKED`. Эксперимент не обходится, ветка реализации
  самостоятельно не выбирается, формулировка «сделаю по варианту А, потом поправим» запрещена;
- документ противоречит коду → STOP и сообщить о расхождении (§0.1.7). Код не подгонять под документ.

BASELINE — текущий HEAD рабочей ветки, а не коммит из шапки плана.
Незакоммиченные изменения worktree не трогать: `.gitignore`, `analysis_options.yaml`,
`pubspec.lock`, `linux/windows/flutter/generated_plugin_*` — чужие, оставить как есть.

## КАК РАБОТАТЬ
1. `TESTS TO ADD FIRST` — до production-изменений, отдельным шагом.
2. Изменения строго в границах `FILES / SYMBOLS`. `DO NOT CHANGE` соблюдать буквально.
3. Существующие тесты не удалять, не ставить skip/Ignore, не ослаблять expect, не менять
   expected value и не подгонять фикстуры. Единственное исключение — тест покрывает код,
   который задача явно удаляет в `DELETE`.
4. Никакого попутного форматирования, переименований, рефакторинга и оптимизаций.
   Никаких новых Manager / Coordinator / Supervisor / Orchestrator.
5. Версии контракта HydraCore не менять. Generated-код — только через
   `dart run pigeon --input pigeons/singbox_api.dart` и `flutter gen-l10n`, руками не править.
6. `STOP CONDITIONS` не обходить. Сработало — остановиться и зафиксировать наблюдение.
7. Секреты не логировать: ни credentials, ни token, ни cookie, ни join_link, ни captcha URL,
   ни IP, ни hostname.

## ВАЛИДАЦИЯ
Все host-side команды из `VALIDATION` карточки обязательны и должны быть зелёными:
analyze / полный `flutter test` (а не только тесты задачи) / gradle unit+lint /
go build,vet,test / verify-скрипты / unittest discover.
Обрезанный вывод раннера за прохождение не считается — перезапусти и дай финальный статус.

`MANUAL SCENARIO`, любые `adb`-проверки и `connectedAndroidTest` в этом PR НЕ выполняются —
проверка на устройстве отложена владельцем до финальной приёмки. Перечисли их в отчёте
как отложенные. Ничего не помечай проверенным, если не запускал.

## РАСХОЖДЕНИЯ КАРТОЧКИ И КОДА: РЕШАЙ САМ ПО ЭТИМ ПРАВИЛАМ
Карточки писались до начала работ, поэтому расходятся с кодом предсказуемым образом.
Ниже — закрытый список таких расхождений. В этих шести случаях НЕ останавливайся:
примени правило, отметь применённое правило в отчёте строкой `RULES APPLIED:` и работай.

1. **Assertion шире scope.** Требуется «ноль вхождений в файле», но часть вхождений
   лежит вне FILES / SYMBOLS. → Assertion действует только в границах FILES / SYMBOLS.
   Остальное оставь и перечисли в отчёте.
2. **Карточка ссылается на несуществующий символ.** Требуется вызвать что-то, чего в
   коде нет (появляется в более поздней задаче). → Используй существующий эквивалент
   на том же уровне (тот же поток, тот же файл), поставь комментарий «переводится на
   `<символ>` в `<TASK ID>`». Новых механизмов не создавай.
3. **FILES / SYMBOLS неполон.** IMPLEMENTATION прямо называет файл, которого нет в
   списке. → Разрешено минимальное изменение в этом файле: ровно то, что названо в
   IMPLEMENTATION, обычно одна строка вызова. Ничего рядом не трогай, факт отметь в отчёте.
4. **Два источника истины после твоей задачи.** Старый механизм остаётся живым рядом с
   новым. → Проверь C16 §1: если окно там перечислено, это норма, закрывает его
   названная там задача. Старый механизм не трогай.
5. **Инвариант выполняется не полностью.** Цель карточки не даёт инварианту сработать
   целиком. → Инварианты устанавливаются частями (`INVARIANTS ESTABLISHED: R.. частично`).
   Проверь §7: если тот же R указан у более поздней задачи — вторую половину делает она.
6. **Красные тесты от предыдущей задачи.** Падает тест, который твой diff не трогал, а
   причина — контракт, изменённый предшественником. → Отдельным ПЕРВЫМ коммитом приведи
   фикстуру/фейк в соответствие с новым контрактом, без правки expect'ов; вторым коммитом
   делай свою задачу. В message первого — «перенос спецификации после `<TASK ID>`».
   Если после этого тест всё ещё красный — СТОП, expect не менять.

7. **STOP CONDITION про гонку, а работа идёт через тот же single-thread executor.**
   → Гонки нет: FIFO одного потока её исключает. Убедись, что работа ставится в очередь
   синхронно и тем же `execute {}`, без `mainHandler.post`, отдельных потоков, локов и
   ожидания результата. Отметь в отчёте.
8. **Символ найден не в том файле, что указан в карточке.** → Путь в FILES / SYMBOLS —
   подсказка, символ — норма. Работай по фактическому адресу внутри того же модуля,
   расширением scope это не считается. Отметь в отчёте.

## ОСТАНАВЛИВАЙСЯ ТОЛЬКО ЗДЕСЬ
Всё, что не попало в шесть правил выше, и в частности:
- карточка ждёт `HB-EXP-*`, а его evidence нет в §8 → BLOCKED, ветку не выбирать;
- пришлось бы ослабить, удалить или подогнать expect существующего теста;
- пришлось бы править verify-скрипт вне явно разрешённого карточкой объёма;
- пришлось бы менять версии контракта HydraCore, ownership или архитектуру;
- сработал STOP CONDITION карточки;
- расхождение не описывается ни одним из шести правил.

## ЧТО НАШЁЛ ВНЕ ЗАДАЧИ
Несвязанный баг, красный не по твоей вине тест, кривой код рядом → в отчёт, не в diff.
Если host-side валидация красная из-за чего-то вне твоих `FILES` — остановись и сообщи,
не «починяй по пути».

## КОММИТ
Один коммит после DONE, только файлы задачи. Если карточка требует обосновать правку
verify-скрипта — отдельной строкой в commit message. `NEXT TASK` не начинать.

Последняя строка commit message — трейлер `Task: <TASK_ID>`. Без него следующий агент
не найдёт твою работу.

После коммита добавь строку в `docs/TASK_LEDGER.md`:
`<TASK_ID> | <repo> | <короткий хеш> | DONE`. При BLOCKED — строку с
`BLOCKED(<что ждёт>)` и без хеша. Это единственный шаг, который делается ПОСЛЕ коммита
и в него не входит.

## ОТЧЁТ
TASK: <TASK_ID>
RESULT: DONE | BLOCKED | STOPPED
RULES APPLIED: <номера правил из раздела расхождений, или "нет">
PRECONDITIONS CHECKED: <коммиты и грепы, по которым определял готовность>
INVARIANTS ESTABLISHED: <R..>
FILES CHANGED: <список>
TESTS ADDED: <список>
VALIDATION OUTPUT: <вывод host-side команд, кратко>
NEGATIVE ASSERTIONS CHECKED: <как именно проверены>
DEVICE CHECKS DEFERRED: <M-сценарии и adb-проверки карточки>
UNRELATED FINDINGS: <или "нет">
STOPPED BECAUSE: <если применимо>
```
