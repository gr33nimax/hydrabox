# HydraBox 2.0 — архитектурный план

Нормативный документ. Единственный источник ответа на вопрос «что делать дальше»
для агентов-исполнителей. Оценок сроков в документе нет намеренно: темп
определяется по фактической работе агентов.

## 0. Правила работы с этим документом

- Документ правят только по решению тимлида. Агент-исполнитель не правит план,
  кроме записи evidence в §9 там, где карточка задачи это прямо требует.
- Единственный источник ответа «выполнен ли предшественник» —
  `docs/HYDRABOX2_TASK_LEDGER.md` плюс `git log`. Поля `STATUS` в карточках
  устаревают и истиной не являются.
- Формат нарядов и правила самостоятельного разрешения блокировок —
  `docs/AGENT_DISPATCH_TEMPLATE.md`, переносится из 1.x без изменений.
- Агенты работают последовательно, по одному в worktree. Два агента в одном
  worktree в 1.x ломали друг другу компиляцию.
- `git add -A` и `git commit -a` запрещены. Только явные пути.
- Каждый коммит несёт трейлер `Task: <ID>`. Последний шаг задачи — строка в ledger.
- Проверки на устройстве в фазах P0–P5 не проводятся. Вся устройственная валидация
  собрана в одну кампанию в P6 (`H2-603`).

## 1. Что такое 2.0 и чем оно не является

HydraBox 2.0 — greenfield-проект на Kotlin Multiplatform и Compose Multiplatform.
Это **не портирование** 1.x. Из 1.x берутся доказавшие себя решения: Kotlin-рантайм,
контракт с HydraCore, инварианты, автоматические тесты. Всё остальное
перепроектируется или пишется заново, если так проще и чище.

Целевые платформы: Android и Windows — первого класса. iOS — не реализуется, но
архитектурно не закрывается.

Что переносится копированием, с минимальной адаптацией:

- рантайм-сервис и его клиент, контроллер libbox, монитор сети, платформенный
  интерфейс — весь Kotlin-слой `android/app/src/main/kotlin/io/hydrabox/client/`;
- контракт с HydraCore: команды, снимок, коды ошибок, версии API;
- инварианты R1–R20 (§3.3);
- автоматические тесты как спецификация (§2).

Что переносится переписыванием логики под тесты:

- генерация конфига ядра, схема outbound'ов, разбор и хранение подписок,
  маршрутные данные — из Dart в `commonMain`.

Что не переносится вообще:

- слой моста Dart↔Kotlin: редьюсер снимка, координатор сессии, контроллер
  намерения, Pigeon-интерфейс и legacy-Map-производители `toLegacy*`;
- `runtimeIntentFile` — вместе с ним снимается задача 1.x `HB-RW-033`;
- `_queuedRestartSuppressed` — признан дефектом плана 1.x;
- подсистема probe — удалена ещё в 1.x, заново не вводится (§3.3, R15);
- скрапинг логов ядра для определения сетевых сбоев — удалён в 1.x `HB-RW-026`.

## 2. Reference snapshot: донор

Решение владельца: `GATE §W` и soak в 1.x **не проводятся**. Оставшиеся задачи 1.x,
относящиеся к Flutter/Dart или исчезающие в 2.0, не закрываются ради формального
завершения плана.

Из этого следует формулировка, которая должна стоять рядом с тегом донора и не
должна быть потеряна: **reference snapshot не является валидированным релизным
baseline.** Он не проходил ни soak, ни проверку на рост памяти и дескрипторов, ни
проверку сплит-туннеля и proxy-only режима. Известные последствия принятого риска:
редкие утечки, race conditions и lifecycle edge-cases рантайма могут быть
скопированы в 2.0 и проявиться на первой alpha. Их поиск отнесён к `H2-603`.

Что фиксирует снапшот:

- коммит и тег ветки `debug` репозитория hydrabox;
- gitlink сабмодуля hydracore и содержимое `libbox.provenance.json`;
- снимок зелёных автоматических тестов: 549 пройденных dart-тестов при 3
  пропущенных и `:app:testDebugUnitTest`. Это приёмочный порог переноса логики:
  в 2.0 не должно остаться ни одного dart-теста без соответствия в `commonTest`
  либо без записи в §9 о причине отсутствия.

## 3. Целевая архитектура

### 3.1 Модули и таргеты

```
:core:contract     команды, снимок, события, генерации, словарь ошибок
:core:runtime      чистый редьюсер и модель дедлайнов
:core:config       генерация конфига ядра
:core:subscription разбор, хранение и обновление подписок
:core:settings     модель настроек и абстракция хранилища
:ui:design         MD3-токены, компоненты, тема
:ui:app            экраны и навигация
:platform:android  VpnService, binder, libbox через AAR, ConnectivityManager
:platform:desktop  helper-сервис, named pipe, libbox через C-ABI, wintun
:platform:ios      заглушка, компилируется, ничего не реализует
```

Таргеты: `androidMain`, `jvmMain`, `iosMain`. `iosMain` существует с первого дня
пустым — чтобы `commonMain` не мог позеленеть только на двух платформах.

Зависимости строго односторонние: `:ui:*` зависит от `:core:*` и не знает о
`:platform:*`; `:platform:*` реализует интерфейсы из `:core:contract` и не знает о
`:ui:*`; `:core:*` не зависит ни от чего платформенного.

### 3.2 Рантайм-контракт

Контракт — единственная граница между UI и рантаймом на всех платформах:

- команды: мутирующие (`START`, `STOP`, `SELECT_OUTBOUND`, `RELOAD`, …) и
  наблюдающие;
- `RuntimeSnapshot` — полное состояние, типизированное, без Map;
- `RuntimeEvent` — поток событий с монотонной `eventSequence`;
- пять величин версионирования как отдельные value-класcы, чтобы `commandGeneration`
  нельзя было передать туда, где ожидается `networkGeneration`. В 1.x это были
  `Int`, и путаница между ними стоила отдельной поправки к плану (§2.4 AMEND);
- транспорт контракта абстрактный: `expect`/`actual`. Android — binder,
  Windows — named pipe, iOS — заглушка.

Исход команды выводится из снимка с дедлайном, а не сопоставлением по
идентификатору. Это решение 1.x, подтверждённое: корреляция по `commandId` создала
бы второй источник истины о состоянии рантайма, что запрещено (§3.3, R2, R19).
`commandId` остаётся в контракте для диагностики и логов.

### 3.3 Инварианты

R1–R20 переносятся из 1.x. Ниже — что с каждым происходит. Текст инварианта в 2.0
формулируется платформенно-нейтрально; агент транскрибирует его в исполняемый тест,
а не пересказывает.

| # | Судьба в 2.0 |
|---|---|
| R1 | Сохраняется. Единственный writer состояния, все записи на потоке serializer. Класс-владелец переименовывается, семантика та же. |
| R2 | Сохраняется и усиливается структурно: типизированный снимок вместо Map, и UI физически не имеет доступа к persisted-файлам. |
| R3 | Сохраняется. Serializer не выполняет операций длительнее ~5 ms и никогда не ждёт результата. |
| R4 | Сохраняется, обобщается. Источник смены сети платформенный (`ConnectivityManager` на Android, свой на Windows), правило «одно семантическое изменение — одна генерация — один rebind» общее. |
| R5 | Сохраняется. Один failure domain — один retry owner. |
| R6 | Сохраняется и становится проверяемым компилятором за счёт value-классов. |
| R7 | Сохраняется. `wantRunning` означает «рантайм обязан быть живым И автовосстановление разрешено». Второго флага не существует. |
| R8 | Сохраняется. Вход в FAILED снимает `wantRunning`, автоматических попыток после FAILED нет. |
| R9 | Сохраняется. Триггеры восстановления платформенные: doze есть только на Android, на Windows нет ни doze, ни убийства процесса системой. |
| R10 | Сохраняется. `PROCESS RUNNING` и `TRANSPORT READY` — разные величины; порог readiness общий (§3.6). |
| R11 | Сохраняется. Фаза UI имеет ровно одного writer — редьюсер снимка. Оговорка про Dart-таймеры заменяется на «ни один платформенный таймер». |
| R12 | Сохраняется. |
| R13 | Сохраняется. Выбранный outbound authoritative только у ядра. |
| R14 | Сохраняется и расширяется на три платформы: версии контракта HydraCore не меняются, расширения только аддитивные. |
| R15 | Становится запретом. Подсистемы probe в 2.0 не существует и она не вводится заново. |
| R16 | Сохраняется, обобщается: lifecycle UI на любой платформе — свёртывание окна, потеря фокуса, пересоздание — не порождает ни одной мутирующей команды и не пересоздаёт транспорт наблюдения. |
| R17 | Сохраняется. Ни один DNS-запрос не переживает смену `networkGeneration`. |
| R18 | Сохраняется. Закрытый словарь `failureDomain` и кодов, общий с HydraCore. |
| R19 | Сохраняется. Ровно один `CommandResult` на принятую мутирующую команду. |
| R20 | Сохраняется и становится структурно истинным: файлов, утверждающих что что-то живо, в 2.0 не создаётся вовсе. |

### 3.4 Что запрещено в `commonMain`

Проверяется в CI, а не на ревью:

- любой тип `android.*`;
- предположение о смерти процесса системой;
- doze, wake, `LOST_GRACE` и всё, что из них выведено;
- `networkGeneration`, полученная напрямую из `ConnectivityManager`;
- форсирование `NetworkStrategyDefault` в диалере — это следствие наличия
  платформенного интерфейса на Android;
- прямые обращения к libbox.

### 3.5 Платформенные слои

**Android.** Двухпроцессная модель сохраняется: UI-процесс и `:core`. Транспорт
контракта — binder. libbox подключается как AAR; `libbox.aar` в git не коммитится
никогда, провенанс описывается `libbox.provenance.json`.

**Windows.** TUN через wintun требует администратора, поэтому архитектура —
неприв GUI плюс привилегированный helper-сервис, внутри которого живёт libbox.
Транспорт контракта — named pipe. Биндинг к libbox — через C-ABI DLL из Kotlin
(Panama либо JNA, решение принимается в `H2-501`); апстрим генерирует C#-биндинг,
эта часть своя. Требуется сертификат подписи кода.

**iOS.** Не реализуется. Держится компилируемым и удовлетворяющим §3.4, чтобы
остаться возможным.

### 3.6 Порог готовности транспорта

Переносится из 1.x без изменений: `READY ⇔ !applicable OR (state ∈ {healthy,
degraded} AND active_lanes ≥ 1)`. Порог живёт в `:core:contract` в одном месте, и
ни один платформенный слой не имеет своей версии этого условия.

## 4. Фазы и задачи

Каждая карточка: цель, предпосылки, границы, критерий готовности. Критерий
готовности проверяем машинно везде, где это возможно.

### P0 — Снапшот и скелет

**H2-000 — зафиксировать reference snapshot.**
Предпосылки: нет. Репозиторий: hydrabox (1.x).
Поставить тег на текущий `debug`; записать в §9 коммит, gitlink hydracore, версию
из `libbox.provenance.json` и результат последнего прогона тестов. Рядом с тегом —
формулировка из §2 о том, что снапшот не валидирован.
Готовность: тег существует; §9 содержит все четыре величины; фраза о
невалидированности присутствует дословно.

**H2-001 — новый репозиторий и граф модулей.**
Предпосылки: `H2-000`.
Создать репозиторий 2.0; завести структуру модулей §3.1 и три таргета; настроить
запрет §3.4 как проверку сборки. Перенести `AGENT_DISPATCH_TEMPLATE.md`. Перенести
`HYDRABOX2_PLAN.md` и ledger в новый репозиторий, в 1.x оставить указатель.
Границы: ни одной строки прикладного кода. Только скелет, версии, зависимости.
Готовность: `commonMain` компилируется под все три таргета; модуль, нарушающий
§3.4, не собирается; попытка зависимости `:core:*` → `:platform:*` не собирается.

**H2-002 — CI.**
Предпосылки: `H2-001`.
Сборка всех таргетов, включая `iosMain`; прогон `commonTest`; проверка §3.4;
публикация артефактов сборки. Локальные сборки инсталляторов и APK запрещены —
только CI.
Готовность: зелёный прогон на пустом скелете; артефакт скачивается.

**H2-003 — ledger и учёт решений.**
Предпосылки: `H2-001`.
Завести `docs/HYDRABOX2_TASK_LEDGER.md` и §10 «реестр решений». Перенести в §10
решения 1.x, которые продолжают действовать (список в §10).
Готовность: ledger содержит строки P0; §10 содержит все перечисленные решения.

### P1 — Контракт и чистый рантайм

**H2-100 — `:core:contract`.**
Предпосылки: `H2-002`.
Команды, `RuntimeSnapshot`, `RuntimeEvent`, пять генераций как value-классы,
закрытый словарь `failureDomain` и кодов ошибок, порог readiness §3.6, абстрактный
транспорт как `expect`.
Границы: версии контракта HydraCore не меняются (R14). Ни одной реализации.
Готовность: попытка передать `commandGeneration` там, где ожидается
`networkGeneration`, не компилируется; словарь ошибок совпадает с Go-словарём
HydraCore (тест сравнения); транспорт не имеет ни одной реализации в `:core`.

**H2-101 — чистый редьюсер.**
Предпосылки: `H2-100`.
`reduce(state, input, ctx): Decision` переносится из 1.x. Побочных эффектов нет:
редьюсер возвращает решение, исполнение эффектов — платформенное.
Границы: ни одной корутины, ни одного таймера, ни одного обращения к вводу-выводу
внутри редьюсера.
Готовность: редьюсер — чистая функция (тест: одинаковый вход даёт одинаковый выход
без внешнего состояния); все ветви состояний из 1.x покрыты.

**H2-102 — инварианты как исполняемые тесты.**
Предпосылки: `H2-101`.
Транскрибировать R1–R20 по таблице §3.3 в тесты `commonTest`. Каждый инвариант —
именованный тест, чтобы падение называло номер.
Границы: R15 оформляется как проверка отсутствия подсистемы probe, а не как
поведенческий тест.
Готовность: двадцать именованных тестов; ни один не помечен пропущенным; для
инвариантов, проверяемых только платформенно, в §9 записано, где именно они
проверяются.

**H2-103 — модель дедлайнов.**
Предпосылки: `H2-101`.
Дедлайны 1.x переносятся значениями: `START_DEADLINE` 45 s, `CHALLENGE_DEADLINE`
120 s, `RECOVERY_DEADLINE` 60 s, `CLOSE_DEADLINE` 5 s, `RELOAD_DEADLINE` 15 s,
`LOST_GRACE` 10 s. Дедлайн — часть `Decision`, а не таймер внутри редьюсера.
Границы: значения не меняются. `LOST_GRACE` помечается Android-специфичным.
Готовность: тест на каждый дедлайн через управляемое время, без реального ожидания.

### P2 — Чистая логика

Идёт параллельно с P1 после `H2-100`. Метод обязателен: **сначала тесты**.

**H2-200 — перенос тестового корпуса.**
Предпосылки: `H2-100`.
18 тысяч строк dart-тестов переносятся в `commonTest` механически, один к одному,
до реализации. Ожидания не ослабляются. Тест, который невозможно перенести,
записывается в §9 с причиной, а не удаляется молча.
Готовность: перенесённые тесты красные по причине отсутствия реализации, а не
компиляции; §9 содержит список непереносимых с причинами.

**H2-201 — генерация конфига ядра.**
Предпосылки: `H2-200`.
Перенос логики `singbox_config_builder`. Сохраняются решения 1.x:
`default_domain_resolver = dns-local`; `domain_resolver: dns-local` для любого
DNS-сервера с не-IP адресом; `dns.final` остаётся прокси-резолвером при наличии
прокси. Подмена маршрута DNS на direct до READY запрещена — это утечка
провайдеру (§10).
Готовность: тесты `H2-200` по конфигу зелёные; сгенерированный конфиг проходит
проверку ядром.

**H2-202 — схема outbound'ов.** Предпосылки: `H2-201`.
Готовность: тесты схемы зелёные, включая `call`/vk-parasite.

**H2-203 — подписки.** Предпосылки: `H2-202`.
Разбор всех поддерживаемых форматов, хранение, обновление.
Границы: секреты не логируются — ни credentials, ни token, ни cookie, ни join_link,
ни captcha URL, ни IP, ни hostname.
Готовность: тесты подписок зелёные; тест на отсутствие секретов в логах.

**H2-204 — маршрутные данные.** Предпосылки: `H2-202`.
Готовность: тесты маршрутизации и adblock зелёные.

**H2-205 — настройки и абстракция хранилища.** Предпосылки: `H2-100`.
Модель настроек в `commonMain`, хранилище — `expect`/`actual`.
Границы: формат хранения выбирается здесь и фиксируется в §10, потому что от него
зависит миграция `H2-600`.
Готовность: настройки читаются и пишутся на всех трёх таргетах, включая заглушку.

### P3 — Android

**H2-300 — транспорт контракта на binder.** Предпосылки: `H2-100`.
Реализация `actual` для абстрактного транспорта; двухпроцессная модель.
Готовность: контрактный тест транспорта проходит поверх binder; тот же тест
пригоден для named pipe в `H2-502`.

**H2-301 — рантайм-сервис.** Предпосылки: `H2-300`, `H2-101`, `H2-103`.
Копирование сервиса и клиента из донора, перепроводка на общий редьюсер:
решения принимает `:core:runtime`, сервис исполняет эффекты и остаётся единственным
writer'ом (R1).
Границы: `toLegacy*`-производители не переносятся. Ни одного Map на границе.
Готовность: `H2-102` зелёные на Android; grep по `toLegacy` пуст по построению.

**H2-302 — контроллер libbox.** Предпосылки: `H2-301`.
Копирование контроллера; libbox как AAR; провенанс.
Границы: `libbox.aar` в git не коммитится, `add -f` запрещён.
Готовность: рантайм стартует и останавливается в инструментальном тесте; провенанс
описывает ровно тот бандл, который в сборке.

**H2-303 — монитор сети и платформенный интерфейс.** Предпосылки: `H2-302`.

## 6. Критерии перехода между фазами

- P0 → P1: скелет собирается под три таргета; нарушение §3.4 не компилируется; CI
  зелёный; ledger заведён.
- P1 → P3: двадцать инвариантов зелёные; редьюсер чистый; дедлайны проверены
  управляемым временем.
- P2 → P6: ни одного перенесённого теста в красном; каждый непереносимый записан в
  §9 с причиной.
- P3 → P6: рантайм стартует и останавливается; grep по `toLegacy` пуст; фаза имеет
  одного writer'а.
- P4 → P6: аудит MD3 не ниже 7 по каждой из десяти категорий; матрица доступности
  expressive на desktop зафиксирована; каждый экран корректен в трёх классах ширины.
- P5 → P6: контрактный тест транспорта зелёный поверх named pipe; туннель
  поднимается и снимается без остатков; инсталлятор подписан.
- P6 → релиз: миграция читает реальный дамп 1.x; чеклист паритета закрыт;
  `H2-603` проведена и её дефекты заведены задачами.

## 7. Риски

**Принятый владельцем.** Reference snapshot не валидирован (§2). Утечки, race
conditions и lifecycle edge-cases рантайма могут быть скопированы и проявиться на
alpha. Митигация — `H2-603`, а не предварительная сертификация 1.x.

**Не принятый, требует измерения.** Доступность expressive-компонентов и
spring-моции в Compose Multiplatform на desktop (`H2-402`). Лимит памяти
`NEPacketTunnelProvider` для четырёх воркеров QUIC (`H2-604`). Сборка `lib_windows`
с тегами форка (`H2-500`). Каждый — измерение до того, как вокруг него построен код.

**Организационный.** Миграция данных (`H2-600`) — единственный пункт, который при
пропуске ломает существующих пользователей и не обнаруживается тестами нового
проекта.

## 8. Запреты на весь проект

- `libbox.aar` в git не коммитится никогда; `add -f` по нему запрещён.
- Локальные сборки APK и инсталляторов не делаются; только CI.
- Секреты не логируются: ни credentials, ни token, ни cookie, ни join_link, ни
  captcha URL, ни IP, ни hostname.
- `git add -A` и `git commit -a` запрещены; force-push запрещён.
- Ветки экспериментов не мержатся в основную.
- Версии контракта HydraCore не меняются; расширения только аддитивные (R14).
- Ничего не удаляется «по пути»: мёртвый код вне границ задачи выносится строкой в
  отчёт.

## 10. Реестр решений

Решения, принятые в 1.x и продолжающие действовать в 2.0. Переспрашивать их не
нужно; отменяет только тимлид.

| Решение | Основание |
|---|---|
| Исход команды выводится из снимка с дедлайном, а не корреляцией по `commandId`. | Корреляция по идентификатору создала бы второй источник истины о состоянии рантайма. `commandId` остаётся для диагностики. |
| Пять генераций — пять раздельных типов, а не `Int`. | В 1.x путаница между `commandGeneration` и `networkGeneration` потребовала отдельной поправки к плану. |
| `NETWORK_CHANGED` не инкрементирует `commandGeneration`. | Смена сети не вытесняет намерение пользователя; устаревание сетевых событий обслуживает `networkGeneration` со своим guard. |
| Подмена маршрута DNS на direct или local до READY запрещена. | Любой успешный ответ до READY идёт вне туннеля, то есть отдаёт провайдеру список доменов на каждом старте. До READY DNS обязан отказывать. |
| Отказ дозвона при нуле активных линий — немедленный. | Ожидание до `WorkerConnectTimeout` выглядит для приложения обрывом сети; быстрый отказ вызывает ретрай. Место ожидания в 1.x было в `QUICRelay.pickPath`. |
| `default_domain_resolver = dns-local`; `domain_resolver: dns-local` для DNS-сервера с не-IP адресом. | DNS-сервер не может разрешать собственное имя через маршрут, который сам обслуживает. |
| Базовая пригодная сеть исключает `TRANSPORT_VPN`. | Иначе собственный туннель считается пригодным апстримом. |
| Прямой вызов обновления интерфейса разрешён только в пути replay при регистрации слушателя. | Первый холодный старт иначе не доводит интерфейс до ядра и старт не завершается. |
| Порог readiness живёт в одном месте контракта. | В 1.x расхождение между «процесс жив» и «транспорт готов» давало ложный READY. |
| Подсистема probe не вводится заново. | Удалена в 1.x; давала второй источник истины и могла задерживать `STOP`. |
| Persisted state описывает только желаемую конфигурацию. | Файл, утверждающий что что-то живо, расходится с реальностью при смерти процесса. |
| Двухпроцессная модель на Android сохраняется. | Отделяет UI от VpnService; граница остаётся, но становится Kotlin↔Kotlin. |

Решения, ожидающие принятия и записи здесь: формат хранилища (`H2-205`), Panama
против JNA (`H2-501`), стратегия деградации дизайн-системы на Windows (`H2-402`).
