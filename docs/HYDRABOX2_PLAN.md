# HydraBox 2.0 — архитектурный план

Нормативный документ. Единственный источник ответа на вопрос «что делать дальше».
Оценок сроков нет намеренно: темп определяется по фактической работе исполнителей.

## 1. Правила работы с документом

- План правит только тимлид. Исполнитель пишет в §11 evidence там, где карточка это
  прямо требует, и добавляет строку в ledger. Больше ничего в плане не меняет.
- Истина о выполненном — `docs/HYDRABOX2_TASK_LEDGER.md` и `git log`. Поля статуса в
  карточках устаревают и истиной не являются.
- Правила поведения исполнителя — `docs/AGENT_DISPATCH_TEMPLATE.md`. Как выдавать
  задачи — `docs/HYDRABOX2_DISPATCH.md`.
- Один исполнитель на worktree. Параллельно ведутся только ветки, помеченные в §7 как
  независимые, и только в разных worktree.
- Одна задача — один PR. Если задача не влезает в один PR, она разбита неверно:
  сообщить, а не растягивать.
- Каждая фаза заканчивается чем-то демонстрируемым (§5). Фаза, после которой нечего
  показать, спроектирована неправильно.
- Позадачных устройственных проверок нет: валидация собрана в кампанию `H2-G04`.
  Два исключения, и оба — приёмки вех, а не проверки задач: **M2** (`H2-B04`, Android)
  и **M6** (`H2-F04`, Windows). Веха, смысл которой — «туннель поднимается», иначе
  недоказуема, а её недоказанность обесценивает раннее снятие риска, ради которого
  фаза B и стоит второй. Обе приёмки короткие, по фиксированному чеклисту, и их
  проводит владелец, а не исполнитель.

## 2. Наследство 1.x

HydraBox 2.0 — greenfield на Kotlin Multiplatform и Compose Multiplatform. Не
портирование. Из 1.x берётся то, что доказало себя, и переносится сознательно —
решение за решением, а не файл за файлом.

### 2.1 Берём как есть

- Инварианты R1–R20 (§4.8) — самое ценное, что появилось в 1.x.
- Контракт с HydraCore: команды, снимок, коды ошибок, версии API. Не меняется (R14).
- Пять величин версионирования и их семантика.
- Значения дедлайнов.
- Порог готовности транспорта.
- Семантика монитора сети: базовая пригодная сеть исключает `TRANSPORT_VPN`; интерфейс
  доводится до ядра в пути replay при регистрации слушателя.
- Решения по DNS и по транспорту `call`/vk-parasite (§12).
- Автоматические тесты как спецификация переносимой логики.

### 2.2 Переделываем, а не копируем

Каждый пункт — ответ на конкретный дефект 1.x, а не улучшение вкуса.

| Что | Как в 1.x | Как в 2.0 | Какой дефект закрывает |
|---|---|---|---|
| Граница UI и рантайма | Pigeon плюс нетипизированные Map, два редьюсера, три контроллера на стороне Dart | один типизированный снимок, одна чистая проекция, UI без логики | читатель брал ключ `error`, а производитель писал `lastError`, и ошибка рантайма молча не доходила до UI |
| Исполнение эффектов | вперемешку с решениями внутри сервиса | эффекты — данные, возвращаемые чистым редьюсером; исполняет платформа | нельзя было протестировать решение без запуска сервиса |
| Время | системные часы внутри логики | дедлайны декларативны, время — зависимость, тесты на виртуальном времени | тесты на дедлайны требовали реального ожидания |
| Восстановление | четыре триггера | один триггер `device_idle_exit`, только Android | эксперимент E7 показал, что три остальных не нужны |
| Секреты в логах | санитайзер как последний барьер | типы, несущие секреты, не имеют рендерера — утечка не компилируется | барьер работает, только если о нём не забыли |
| Хранилище | Hive плюс разрозненные миграции | версионированная схема с первого шага, импорт 1.x — отдельный одноразовый читатель | миграция задним числом дороже и рискованнее |
| Скрапинг логов ядра | разбор строк лога для сетевых сбоев | нет | удалено ещё в 1.x |

### 2.3 Не переносим

- Слой моста Dart↔Kotlin целиком: редьюсер снимка, координатор сессии, контроллер
  намерения, Pigeon, производители `toLegacy*`.
- `runtimeIntentFile` — вместе с ним снимается задача 1.x `HB-RW-033`.
- `_queuedRestartSuppressed` — признан дефектом плана 1.x.
- Подсистема probe — удалена в 1.x, заново не вводится (R15).
- Три из четырёх триггеров восстановления.

## 3. Reference snapshot

Решение владельца: `GATE §W` и soak в 1.x не проводятся; оставшиеся задачи 1.x,
привязанные к Flutter/Dart или исчезающие в 2.0, не закрываются.

Следствие, которое должно стоять рядом с тегом донора: **reference snapshot не
является валидированным релизным baseline.** Не проверялись soak, рост памяти и
дескрипторов, сплит-туннель, proxy-only. Принятый риск: редкие утечки, race
conditions и lifecycle edge-cases рантайма могут быть скопированы и проявиться на
первой alpha, где и будут исправляться. Поиск отнесён к `H2-G04`.

Зафиксировано в `H2-A01`: тег `v1.x-reference-snapshot`, коммит, gitlink hydracore,
версия из `libbox.provenance.json`, числа последнего прогона тестов.

## 4. Архитектура

### 4.1 Принципы

**Одна истина о состоянии.** `RuntimeSnapshot` — единственное описание живого
состояния. Ни UI, ни нотификация, ни плитка, ни файл не выводят состояние иначе.

**Решения отделены от эффектов.** Ядро — чистая функция. Она не запускает, не
останавливает, не ждёт и не смотрит на часы; она возвращает решение. Всё, что
взаимодействует с миром, исполняет платформа и сообщает результат обратно как вход.

**Платформа различается только исполнителем эффектов.** Android и Windows не имеют
своих версий логики, своих порогов и своих таймеров. Различие сведено к реализации
эффектов и транспорта.

**Типы вместо соглашений.** Пять генераций — пять типов. Секретные значения — свой
тип. Нарушение должно не компилироваться, а не обнаруживаться на ревью.

**Каждая фаза демонстрируема.** Порядок работ выстроен так, чтобы риск снимался
раньше, чем на нём строят код, и чтобы после каждой фазы было что показать.

### 4.2 Модули

```
:core:model         кросс-сквозные примитивы: OperationState, идентификаторы, база ошибок
:core:contract      команды, снимок, события, генерации, коды ошибок, wire-схема
:core:runtime       чистый редьюсер, эффекты как данные, модель дедлайнов
:core:projection    Snapshot -> ScreenState, чистая функция, без Compose
:core:storage       версионированное хранилище, движок через expect/actual
:core:settings      модель настроек
:core:subscription  модели, парсеры, хранилище подписок
:core:config        генерация конфига ядра
:core:diagnostics   типизированные события, структурная защита секретов, read-модель логов
:core:update        проверка и загрузка обновлений приложения
:ui:design          токены MD3, тема, компоненты
:ui:app             экраны; читают ScreenState, логики не содержат
:platform:android   VpnService, binder, libbox через AAR, ConnectivityManager
:platform:desktop   helper-сервис, named pipe, libbox через C-ABI, wintun
```

Направление зависимостей односторонне и проверяется сборкой: `:ui:*` зависит от
`:core:*` и не знает о `:platform:*`; `:platform:*` реализует интерфейсы
`:core:contract` и не знает о `:ui:*`; `:core:*` не зависит ни от чего платформенного;
`:core:runtime` не зависит даже от `:core:storage`. `:core:model` не зависит ни от
чего и является основанием для всех остальных.

Таргеты: `androidMain`, `jvmMain`. iOS — §13.

### 4.3 Рантайм: эффекты как данные

```
reduce(state: RuntimeState, input: RuntimeInput, ctx: ReduceContext): Decision

Decision(
  state:    RuntimeState,      // новое состояние, единственный путь его изменения
  effects:  List<Effect>,      // что исполнить платформе
  timers:   List<TimerOp>,     // какие дедлайны завести и какие снять
  events:   List<RuntimeEvent> // что издать наружу
)
```

`Effect` — закрытая иерархия: старт ядра, остановка, применение конфига, выбор
outbound'а, обновление интерфейса, пробуждение ядра. Исполнитель эффектов —
платформенный, единственный, и он не принимает решений: результат каждого эффекта
возвращается в ядро как `RuntimeInput`.

`ReduceContext` несёт только чтение: текущее время как значение, а не как источник, и
неизменяемые параметры окружения. Внутри `reduce` нет ни корутин, ни ввода-вывода, ни
обращения к часам, ни ожидания.

Дедлайны декларативны: ядро просит завести таймер, платформа его заводит, срабатывание
приходит как вход. Значения переносятся из 1.x без изменений: `START_DEADLINE` 45 s,
`CHALLENGE_DEADLINE` 120 s, `RECOVERY_DEADLINE` 60 s, `CLOSE_DEADLINE` 5 s,
`RELOAD_DEADLINE` 15 s, `LOST_GRACE` 10 s (Android-специфичен).

Почему так: в 1.x решение и его исполнение жили в одном классе, поэтому проверить
поведение можно было только запустив сервис. Здесь весь набор состояний проверяется
как таблица, а платформенный слой остаётся тонким и скучным.

### 4.4 Контракт и транспорт

`:core:contract` содержит команды (мутирующие и наблюдающие), `RuntimeSnapshot`,
`RuntimeEvent` с монотонной `eventSequence`, пять генераций как отдельные типы,
закрытый словарь `failureDomain` и кодов ошибок, порог готовности и wire-схему.

Порог готовности живёт в одном месте: `READY ⇔ !applicable OR (state ∈ {healthy,
degraded} AND active_lanes ≥ 1)`. Ни один платформенный слой не имеет своей версии
этого условия.

Транспорт — `expect`/`actual` поверх одной wire-схемы. Один и тот же контрактный тест
обязан проходить на binder и на named pipe; второй тест для второй платформы не
пишется. Это и есть проверка того, что граница действительно одна.

Исход команды выводится из снимка с дедлайном, а не сопоставлением по `commandId`:
корреляция по идентификатору создала бы второй источник истины. `commandId` остаётся
для диагностики.

### 4.5 Проекция и UI

```
project(
  runtime:       RuntimeSnapshot,          // :core:contract
  catalog:       SubscriptionCatalog,      // :core:subscription — настроенная часть
  subscriptions: SubscriptionsState,       // :core:subscription — список и операции
  settings:      Settings,                 // :core:settings
  diagnostics:   DiagnosticsState,         // :core:diagnostics
  update:        UpdateState,              // :core:update
  backup:        OperationState<BackupOutcome> // :core:storage
): ScreenState
```

Чистая функция в `:core:projection`, без Compose и без платформенных типов. Всё, что
UI показывает — фаза, доступность действий, тексты ошибок, счётчики, состояние
нотификации и плитки — выводится здесь и покрыто тестами.

**Владелец каждой read-модели ровно один**, и проекция ничего не производит, только
соединяет:

| Данные | Владелец-производитель | Почему там |
|---|---|---|
| фаза, состояние рантайма, генерации, последняя ошибка | `:core:runtime` через снимок в `:core:contract` | R2: живая истина о рантайме только здесь |
| счётчики и скорость трафика | там же, снимок | приходят потоком статуса из ядра; троттлинг частоты — на стороне рантайма (R16), UI частоту не запрашивает |
| живая часть каталога: группы, текущий выбор, задержки url-test | там же, снимок | сообщает ядро, а не подписка |
| настроенная часть каталога: outbound'ы, цепочки, группы как описаны | `:core:subscription` | это конфигурация, а не живое состояние |
| список подписок, срок действия, состояние обновления и его ошибка | `:core:subscription` | не рантайм: персистентное состояние плюс операция в полёте |
| настройки | `:core:settings` | — |
| журнал и уровень логирования, состояние экспорта диагностики | `:core:diagnostics` | — |
| наличие обновления, загрузка, история изменений | `:core:update` | в 1.x это был сервис на 42 КБ без владельца; отдельный модуль оставляет `:core:settings` моделью, а не сервисом |
| состояние резервного копирования | `:core:storage` | резервная копия — операция над версионированной схемой, а не настройка |

Соединение двух половин каталога — настроенной и живой — происходит только в проекции.
Это единственное место, где они встречаются, и это сознательно: в 1.x они смешивались
в нескольких местах и расходились.

Любая операция вне рантайма — обновление подписки, загрузка обновления, резервное
копирование — описывается одним общим типом `OperationState` из `:core:model`, а не
своим перечислением в каждой подсистеме. Пять похожих, но разных форм превращают
проекцию в набор адаптеров.

**Ограничение, удерживающее R2 и R11.** Ни одна read-модель, кроме снимка, не имеет
права утверждать, жив ли туннель. Сборка потоков в один вход проекции — композиционный
корень в `:ui:app`, и он обязан быть тупым: только `combine` и вызов `project`. Ни
одного условия, ни одного таймера, ни одного сравнения состояний в нём быть не может;
это проверяется на ревью и должно оставаться в пределах одного экрана кода.

`:ui:app` не содержит логики: ни таймеров, ни собственных фаз, ни решений о том,
можно ли нажать кнопку. Это прямое следствие того, что в 1.x тумблер и попапы имели
собственное представление о состоянии и расходились с рантаймом.

### 4.6 Диагностика и секреты

События диагностики типизированы. Значения, способные нести секрет — credentials,
token, cookie, join_link, captcha URL, IP, hostname — имеют собственный тип, у
которого нет рендерера в строку. Попытка залогировать такое значение не компилируется.

Санитайзер как «последний барьер» из 1.x не воспроизводится: барьер, о котором можно
забыть, рано или поздно забывают. Здесь забыть нельзя.

### 4.7 Хранилище

`:core:storage` — версионированная схема с первого шага: у каждой сущности есть версия,
и переход между версиями — явная миграция с тестом. Движок платформенный через
`expect`/`actual`, модель — общая.

Импорт данных 1.x из Hive — отдельный одноразовый читатель в `H2-G01`, а не часть
модели. Он не имеет права влиять на форму новой схемы.

### 4.8 Инварианты

R1–R20 переносятся из 1.x. Формулировка в 2.0 платформенно-нейтральна; исполнитель
транскрибирует инвариант в именованный тест, а не пересказывает.

| # | Судьба в 2.0 |
|---|---|
| R1 | Сохраняется. Единственный writer состояния — путь через `reduce`; иного способа изменить состояние не существует по построению. |
| R2 | Сохраняется и усиливается: снимок типизирован, UI не имеет доступа к persisted-состоянию, проекция чистая. |
| R3 | Сохраняется структурно: внутри `reduce` нет ввода-вывода и ожидания, поэтому serializer нечем занять. |
| R4 | Сохраняется, обобщается: источник смены сети платформенный, правило «одно семантическое изменение — одна генерация — один rebind» общее. |
| R5 | Сохраняется. Один failure domain — один retry owner. |
| R6 | Сохраняется и проверяется компилятором за счёт раздельных типов генераций. |
| R7 | Сохраняется. `wantRunning` означает «рантайм обязан быть живым И автовосстановление разрешено». Второго флага нет. |
| R8 | Сохраняется. Вход в FAILED снимает `wantRunning`; автоматических попыток после FAILED нет. |
| R9 | Сохраняется. Восстановление ограничено счётчиком; единственный триггер — `device_idle_exit`, только Android. |
| R10 | Сохраняется. `PROCESS RUNNING` и `TRANSPORT READY` — разные величины; порог один (§4.4). |
| R11 | Сохраняется и становится структурным: фазу вычисляет проекция, у UI нет способа её написать. |
| R12 | Сохраняется. События издаются из одного места, `eventSequence` монотонна. |
| R13 | Сохраняется. Выбранный outbound authoritative только у ядра; команда создаёт намерение, а не истину. |
| R14 | Сохраняется и расширяется на обе платформы: версии контракта HydraCore не меняются, расширения аддитивные. |
| R15 | Становится запретом: подсистемы probe не существует и она не вводится. |
| R16 | Сохраняется, обобщается: lifecycle UI на любой платформе — свёртывание, потеря фокуса, пересоздание — не порождает мутирующих команд и не пересоздаёт транспорт наблюдения. |
| R17 | Сохраняется. Ни один DNS-запрос не переживает смену `networkGeneration`. |
| R18 | Сохраняется. Закрытый словарь домена и кода, общий с HydraCore. |
| R19 | Сохраняется. Ровно один `CommandResult` на принятую мутирующую команду. |
| R20 | Сохраняется и становится истинным по построению: файлов, утверждающих что что-то живо, не создаётся. |

### 4.9 Запреты в `commonMain`

Проверяются сборкой, не ревью:

- любой тип `android.*`;
- любой тип `java.*`, `javax.*`, `kotlin.jvm.*` и любой JVM-only API стандартной
  библиотеки;
- зависимость без multiplatform-артефактов, включающих Apple-таргеты;
- предположение о смерти процесса системой; doze, wake, `LOST_GRACE` и производное;
- генерация сети, полученная напрямую из `ConnectivityManager`;
- прямые обращения к libbox;
- системные часы и любой источник времени, кроме переданного значения.

Про JVM-only отдельно, потому что это неочевидно и это главный пункт. `androidMain` и
`jvmMain` — оба JVM, поэтому `commonMain` с `java.io` скомпилируется на обоих и при
этом окажется непригодным для Kotlin/Native, то есть закроет `iosMain` в будущем.
Компилятор этого не поймает: доказать Native-чистоту мог бы только реальный
Native-таргет, но iOS требует хоста macOS, а `linuxX64` и `mingwX64` обеспечены
зависимостями хуже самого iOS. Поэтому гарантия держится правилом, и правило обязано
быть машинным. Подстановки: `kotlinx-datetime` вместо `java.time`, `okio` либо
`kotlinx-io` вместо `java.io`/`java.nio`, `kotlinx-serialization`,
`kotlinx-coroutines` без опоры на `Dispatchers.IO`, криптография — multiplatform либо
`expect`/`actual`.

### 4.10 Платформенные слои

**Android.** Двухпроцессная модель сохраняется: UI-процесс и `:core`. Транспорт —
binder. libbox как AAR; `libbox.aar` в git не коммитится никогда, провенанс описывает
`libbox.provenance.json`. Единственный триггер восстановления — `device_idle_exit`.

**Windows.** wintun требует администратора, поэтому неприв GUI плюс привилегированный
helper-сервис, внутри которого живёт libbox. Транспорт — named pipe. Биндинг к libbox —
C-ABI DLL из Kotlin; выбор Panama против JNA принимается в `H2-F02` и записывается в
§12. Апстрим генерирует C#-биндинг, эта часть своя. Нужен сертификат подписи кода.

## 5. Вехи

Веха — это то, что можно показать. Фаза без вехи не заканчивается.

| Веха | Что демонстрируется | Закрывается фазой |
|---|---|---|
| M1 | скелет собирается под оба таргета, запрещённый импорт ломает сборку, CI зелёный | A |
| M2 | Android поднимает туннель по конфигу с диска и опускает его; трафик идёт | B |
| M3 | тот же туннель управляется настоящим ядром; двадцать инвариантов зелёные | C |
| M4 | конфиг строится из реальной подписки; вся логика перенесена и зелёная | D |
| M5 | полноценный интерфейс на Android, аудит MD3 пройден | E |
| M5b | интерфейс проверен на пользу, правки внесены, экраны покрыты тестами | E2 |
| M6 | Windows поднимает туннель тем же ядром и тем же контрактом | F |
| M7 | alpha на обеих платформах, кампания валидации проведена | G |

M2 стоит вторым не случайно. Он снимает сразу три риска — биндинг libbox, процессную
границу и wire-схему — до того, как на них построены логика и интерфейс. Цена — один
временный stub-редьюсер, который удаляется в C.

## 6. Фазы и задачи

Карточка: цель, предпосылки, границы, критерий готовности. Критерий готовности
проверяем машинно везде, где это возможно.

### Фаза A — Фундамент → M1

**H2-A01 — reference snapshot и репозиторий.** Предпосылки: нет.
Тег донора и четыре величины §3 в §11. Репозиторий 2.0, модули §4.2, таргеты
`androidMain` и `jvmMain`, направление зависимостей §4.2 закреплено сборкой.
Границы: ни строки прикладного кода.
Готовность: тег существует с формулировкой о невалидированности; все модули §4.2
собираются; обратная зависимость `:core:* -> :platform:*` не собирается.
Исторически выполнено как `H2-000` и `H2-001` (§14); недостающее добирает `H2-A02`.

**H2-A02 — машинные запреты §4.9.** Предпосылки: `H2-A01`.
Убрать `:platform:ios` и iOS-таргеты (§13). Добавить недостающие модули §4.2:
`:core:projection`, `:core:storage`, `:core:diagnostics`. Включить проверку всех
запретов §4.9 как проверку сборки.
Границы: ни строки прикладного кода.
Готовность: `import java.io.File` в `commonMain` ломает сборку с внятным сообщением;
то же для `android.*`; `:platform:ios` отсутствует; §11 содержит выбранный механизм.

**H2-A03 — CI.** Предпосылки: `H2-A02`.
Сборка обоих таргетов, `commonTest`, проверки §4.9, публикация артефактов. Локальные
сборки APK и инсталляторов запрещены.
Готовность: зелёный прогон; артефакт скачивается; нарушение §4.9 роняет CI.

**H2-A04 — контракт.** Предпосылки: `H2-A02`.
`:core:contract` по §4.4: команды, снимок, события, пять генераций отдельными типами,
словарь домена и кодов, порог готовности, wire-схема.
Границы: версии контракта HydraCore не меняются (R14). Ни одной реализации транспорта.
Готовность: передача одной генерации вместо другой не компилируется; словарь кодов
совпадает с Go-словарём HydraCore (тест сравнения); порог готовности существует
ровно в одном месте.

**H2-A06 — `:core:model`.** Предпосылки: `H2-A02`.
Кросс-сквозные примитивы: `OperationState` для любой операции вне рантайма,
идентификаторы, база типов ошибок.
Границы: модуль не зависит ни от чего. Ни одной подсистемной сущности сюда не класть —
это основание, а не свалка общего.
Готовность: модуль не имеет зависимостей; `OperationState` покрыт тестами переходов;
попытка добавить зависимость роняет сборку.

**H2-A05 — ledger и реестр решений.** Предпосылки: `H2-A01`.
Готовность: ledger содержит строки фазы A; §12 содержит перенесённые решения.

### Фаза B — Ходячий скелет на Android → M2

Цель фазы — поднять туннель минимальным путём и тем снять риск биндинга, процессной
границы и wire-схемы. Всё, что можно отложить, откладывается: ни подписок, ни
настроек, ни дизайна.

**H2-B01 — транспорт на binder.** Предпосылки: `H2-A04`.
`actual` для транспорта, двухпроцессная модель, контрактный тест wire-схемы.
Границы: контрактный тест пишется один раз и обязан быть пригодным для named pipe;
платформенных ветвлений в тесте быть не должно.
Готовность: контрактный тест зелёный поверх binder; снимок доезжает до UI-процесса
типизированным.

**H2-B02 — libbox и провенанс.** Предпосылки: `H2-B01`.
Подключение AAR, `libbox.provenance.json`, gitlink hydracore.
Границы: `libbox.aar` не коммитится; sha256 берутся из опубликованного манифеста, а не
считаются локально.
Готовность: версия ядра читается из Kotlin; провенанс сходится с манифестом.

**H2-B03 — VpnService и stub-ядро.** Предпосылки: `H2-B02`.
Минимальный сервис в `:core`-процессе, VpnService, foreground-нотификация. Решения
принимает временный stub, реализующий тот же интерфейс, что и будущее ядро.
Границы: stub помечен в коде как временный и подлежащий удалению в `H2-C04`. Логика в
stub не наращивается: любое усложнение — признак, что пора в фазу C.
Готовность: сервис стартует и останавливается; нотификация отражает снимок.

**H2-B04 — туннель по конфигу с диска.** Предпосылки: `H2-B03`.
Экран из одной кнопки; конфиг читается из файла, положенного вручную.
Границы: ни генерации конфига, ни подписок, ни настроек.
Готовность исполнителя, host-side: сборка зелёная; конфиг читается и передаётся ядру;
инструментальный тест доводит состояние до RUNNING и обратно.
Приёмка M2 — за владельцем, отдельным шагом `H2-B04-ACC`. Задача исполнителя
считается выполненной по host-side критерию; он не ждёт устройства и переходит к
фазе C.

**H2-B04-ACC — приёмка M2.** Владелец, одно устройство, фиксированный чеклист.
Рабочий конфиг берётся из установленного 1.x, чтобы не готовить его отдельно:
`adb shell run-as io.hydrabox.client cat files/singbox-config.json`. Отладочная сборка
это разрешает.
Чеклист, три повтора, ничего сверх него:
  1. холодный старт, нажатие кнопки, состояние доходит до RUNNING;
  2. один HTTP-запрос из другого приложения проходит через туннель;
  3. остановка: туннель снят, системный индикатор VPN погас;
  4. после остановки не осталось ни сетевого адаптера, ни процесса `:core`.
Не входит в M2 и не проверяется здесь: хендоверы, doze, смерть процесса, рост памяти
и дескрипторов, сплит-туннель, proxy-only. Всё это — `H2-G04`.
Готовность: три повтора чеклиста пройдены; результат записан в §11. Это M2.

### Фаза C — Настоящее ядро → M3

**H2-C01 — чистый редьюсер и эффекты как данные.** Предпосылки: `H2-A04`.
`reduce` и `Decision` по §4.3. Перенос таблицы состояний 1.x.
Границы: ни корутин, ни ввода-вывода, ни часов внутри `reduce`.
Готовность: тест доказывает чистоту — одинаковый вход даёт одинаковый выход без
внешнего состояния; все ветви состояний покрыты; ни один эффект не исполняется внутри
ядра.

**H2-C02 — дедлайны на виртуальном времени.** Предпосылки: `H2-C01`.
Готовность: каждый дедлайн §4.3 проверен без реального ожидания; значения не изменены.

**H2-C03 — инварианты как тесты.** Предпосылки: `H2-C01`.
Двадцать именованных тестов по §4.8; падение называет номер инварианта.
Границы: R15 — проверка отсутствия подсистемы, а не поведения.
Готовность: двадцать тестов, ни один не пропущен; для проверяемых только платформенно

**H2-C04 — замена stub на ядро.** Предпосылки: `H2-C01`, `H2-C02`, `H2-B04`.
Платформенный исполнитель эффектов; stub удаляется.
Границы: удаляется, а не отключается флагом.
Готовность: grep по имени stub пуст; сценарий M2 повторяется на настоящем ядре;
`H2-C03` зелёные на Android. Это M3.

**H2-C06 — трафик и живой каталог в снимке.** Предпосылки: `H2-C04`.
Расширение снимка величинами, которые сообщает ядро: счётчики и скорость трафика;
группы, текущий выбор, задержки url-test.
Границы: троттлинг частоты выдачи — на стороне рантайма, как в 1.x (R16); UI частоту не
запрашивает и о ней не знает. Настроенная часть каталога сюда не попадает — она
принадлежит `:core:subscription`. Версии контракта HydraCore не меняются, расширение
аддитивное (R14).
Готовность: счётчики и живой каталог доезжают до UI-процесса через снимок; смена
foreground не порождает мутирующих команд (R16); тест на аддитивность расширения.

**H2-C05 — диагностика и защита секретов.** Предпосылки: `H2-A04`.
`:core:diagnostics` по §4.6.
Готовность: попытка залогировать секретный тип не компилируется; тест на это
существует и является тестом компиляции, а не строкового поиска.

### Фаза D — Логика → M4

Метод — вертикальный срез по подсистеме: тесты подсистемы, реализация, зелено,
следующая подсистема. Единого предварительного переноса всего тестового корпуса не
делается: он даёт тысячи красных тестов и ни одной работающей подсистемы.

Правила, общие для всех задач D:

- два коммита: первый переносит тесты подсистемы и оставляет их красными по причине
  отсутствия реализации, второй добавляет реализацию и делает их зелёными. Один коммит
  на оба шага не принимается — тогда не видно, что тест предшествовал коду;
- переносится весь корпус подсистемы, а не выбранные тесты, иначе «зелено» ничего не
  означает;
- ожидания не ослабляются: непрошедший тест — дефект реализации, пока не доказано
  обратное;
- непереносимый тест записывается в §11 с причиной и не удаляется молча;
- каждая задача добавляет в §11 строку соответствия: какие dart-файлы тестов перенесены
  и куда. Учёт складывается инкрементально.

Порядок задан зависимостями кода-донора, а не удобством: `singbox_config_builder`
импортирует модели и парсеры подписок и хранилище настроек, а `outbound_schema`
используется разбором подписок. Поэтому генерация конфига идёт последней.

**H2-D01 — версионированное хранилище.** Предпосылки: `H2-A02`.
`:core:storage` по §4.7. Движок выбран тимлидом: **SQLDelight**, единственный для всех
данных — и для настроек, и для подписок. Второго движка не вводится.

Устройство модуля:
- запросы и схема — в `commonMain`; драйвер — платформенный через `expect`/`actual`
  (Android — SQLite-драйвер AndroidX, desktop — JDBC-драйвер в `jvmMain`).
  JVM-only артефакт драйвера в `commonMain` не попадает, §4.9 соблюдается;
- миграции — файлами миграций SQLDelight с номерами версий; проверка целостности
  цепочки миграций включается в CI и обязана падать, если цепочка не воспроизводит
  актуальную схему;
- настройки живут в том же движке. Отдельного key-value хранилища для них нет:
  два движка означают две несогласованные механики миграции;
- секреты хранятся зашифрованными на уровне поля, а не базы. Ключ выдаёт
  `expect`/`actual` провайдер: на Android — с опорой на Keystore, на desktop — DPAPI
  либо файл ключа. Шифруется ровно то, что имеет секретный тип §4.6; связь с §4.6
  прямая — тип, у которого нет рендерера в строку, и есть тип, который шифруется.

Границы: импорт 1.x здесь не делается и на форму схемы не влияет (`H2-G01`). Схема
проектируется под данные 2.0, а не под форму Hive-боксов.
Готовность: тест на переход между двумя версиями схемы; проверка цепочки миграций в
CI зелёная; движок работает на обоих таргетах; секретное поле в базе нечитаемо без
провайдера ключа, и на это есть тест.

**H2-D02 — настройки.** Предпосылки: `H2-D01`.
Готовность: тесты настроек зелёные.

**H2-D03 — схема outbound'ов и модели подписок.** Предпосылки: `H2-D02`.
Готовность: тесты схемы зелёные, включая `call`/vk-parasite.

**H2-D04 — подписки.** Предпосылки: `H2-D03`.
Разбор всех поддерживаемых форматов, хранение, обновление.
Границы: секреты — только через типы §4.6.
Готовность: тесты подписок зелёные; тест на отсутствие секретов в диагностике.

**H2-D05 — маршрутные данные.** Предпосылки: `H2-A02`.
Границы: независима от `H2-D06`, данные приходят параметрами.
Готовность: тесты маршрутизации и adblock зелёные.

**H2-D06 — генерация конфига.** Предпосылки: `H2-D04`, `H2-D02`.
Сохраняются решения 1.x: `default_domain_resolver = dns-local`;
`domain_resolver: dns-local` для DNS-сервера с не-IP адресом; `dns.final` остаётся
прокси-резолвером при наличии прокси; подмена маршрута DNS на direct до READY запрещена
как утечка (§12).
Готовность: тесты конфига зелёные; сгенерированный конфиг проходит проверку ядром;
туннель из фазы B поднимается на сгенерированном конфиге, а не на файле с диска. Это M4.

**H2-D08 — `:core:update`.** Предпосылки: `H2-A06`, `H2-D01`.
Проверка наличия обновления, загрузка, история изменений; состояние — через
`OperationState`.
Границы: ни одного решения о рантайме.
Готовность: тесты состояний «нет обновления, доступно, загружается, ошибка».

**H2-D09 — резервное копирование.** Предпосылки: `H2-D01`.
Экспорт и импорт поверх версионированной схемы, read-модель через `OperationState`.
Границы: своего формата не вводить, только версионированная схема §4.7; импорт из 1.x —
это `H2-G01`, здесь его нет.
Готовность: круговой рейс экспорт-импорт совпадает поле в поле; импорт версии на
единицу ниже проходит через миграцию.

**H2-D10 — read-модель диагностики.** Предпосылки: `H2-C05`.
Журнал, уровень логирования, состояние экспорта.
Границы: секреты — только через типы §4.6; экспорт не может их обойти.
Готовность: тест на то, что экспорт диагностики не содержит секретных значений.

**H2-D07 — проекция.** Предпосылки: `H2-C06`, `H2-D02`, `H2-D04`, `H2-D08`, `H2-D09`,
`H2-D10`, `H2-A06`.
`:core:projection` по §4.5, с полным набором read-моделей и владельцами из таблицы того
же раздела.
Границы: без Compose и без платформенных типов; проекция ничего не производит, только
соединяет. Соединение настроенной и живой половин каталога происходит здесь и только
здесь.
Готовность: проекция — чистая функция; фаза, доступность действий, тексты ошибок,
счётчики и состояния операций покрыты тестами; ни один платформенный таймер не
участвует; композиционный корень в `:ui:app` не содержит ни одного условия.

### Фаза E — Дизайн-система и интерфейс → M5

Дизайн переделывается, а не переносится: из 1.x берётся инвентарь экранов и решения,
вёрстка пишется заново.

**H2-E01 — токены и тема.** Предпосылки: `H2-A03`.
MD3: только токены `md.sys` через `MaterialTheme.colorScheme`/`typography`/`shapes`;
пять уровней surface-контейнеров; высота тональной поверхностью, не тенями; `outline`
для смысловых границ, `outline-variant` для разделителей; девять токенов радиусов;
отступы 8 dp. Динамический цвет от seed, брендовый seed как fallback — на Windows
системного источника цвета нет.
Границы: ни одного литерального цвета, ни одного `Color(0x…)`, ни одного произвольного
радиуса.
Готовность: grep по хардкодным цветам и радиусам пуст; светлая и тёмная темы
консистентны; три уровня контраста поддержаны.

**H2-E02 — компоненты.** Предпосылки: `H2-E01`.
Только те компоненты, что нужны инвентарю экранов.
Готовность: аудит MD3 по десяти категориям не ниже 7 по каждой; неиспользуемых
компонентов нет.

**H2-E03 — адаптивные скаффолды и деградация на desktop.** Предпосылки: `H2-E02`.
Windows — платформа первого класса, поэтому телефонная вёрстка как единственная
запрещена.

Стратегия деградации выбрана тимлидом: **возможности разрешаются один раз в теме,
экраны о платформе не знают.**

- `:ui:design` предоставляет тему, которая разрешает две величины: схему моции
  (пружинная либо основанная на длительностях) и уровень компонентов (expressive
  либо стандартный M3). Разрешение происходит в одном месте;
- ни один экран и ни один компонент в `:ui:app` не ветвится по платформе. Проверяется
  запретом: обращение к платформенному признаку из `:ui:app` не собирается;
- направление подмены: expressive-компонент заменяется стандартным M3 с той же
  семантической ролью и теми же токенами; пружина заменяется парой
  «кривая плюс длительность» из MD3 — emphasized 500 ms для крупных переходов,
  decelerate 400 ms на появление, accelerate 200 ms на исчезновение, standard для
  остального;
- компонент, у которого нет стандартного аналога с той же ролью, не используется
  вовсе, ни на одной платформе. Это и есть предохранитель против расхождения:
  наименьший общий знаменатель применяется поштучно, а не ко всей системе;
- вёрстка и информационная архитектура на платформах идентичны. Различаться
  позволено только моции и оформлению компонентов. Пиксельный паритет не является
  целью: эталон визуальной проработки — Android с динамическим цветом, desktop
  обязан быть корректным и спокойным, а не одинаковым;
- сокращённая моция: пружины и длинные переходы уважают системную настройку
  уменьшения анимации; на desktop поведение по умолчанию консервативнее.

Измерение — часть задачи: собрать матрицу фактической доступности expressive и
пружин в Compose Multiplatform на desktop и записать её в §11. Матрица определяет
таблицу подмен, которая живёт и в §11 как evidence, и в `:ui:design` как код.

Готовность: каждый экран корректен в трёх классах ширины; матрица в §11; таблица
подмен полна — для каждого используемого expressive-компонента либо есть аналог, либо
компонент исключён из инвентаря с записью в §11; тестовый набор `:ui:design` рендерит
каждый компонент в обоих режимах возможностей, поэтому отсутствие подмены падает на
тестах, а не на Windows в рантайме; обращение к платформенному признаку из `:ui:app`
не собирается.

**Инвентарь экранов закрыт.** Список ниже — полный и нормативный. Экран, которого в
нём нет, в 2.0 не появляется без решения тимлида. «Перенести весь инвентарь 1.x» не
подтверждаю: в 1.x девятнадцать страниц, часть из них не релизная.

**H2-E04 — путь подключения.** Предпосылки: `H2-E03`, `H2-D07`, `H2-C06`.
Экраны: главный (состояние подключения, кнопка, активный прокси, карточка активной

**H2-E05 — подписки и прокси.** Предпосылки: `H2-E04`, `H2-D04`, `H2-C06`.

с историей изменений внутри экрана, а не отдельной; логи и диагностика; welcome;

Действиями внутри настроек, а не экранами: экспорт и импорт резервной копии. Формат
резервной копии — версионированная схема §4.7, своего формата не вводить.
Готовность: инвентарь закрыт целиком; ни один экран не читает persisted-состояние для
живых величин; ни один экран не ветвится по платформе. Это M5.

### Фаза E2 — Аудит интерфейса и тесты экранов → M5b

Фаза стоит между E и G сознательно. После `H2-E06` Android уже собирается и им можно
пользоваться, но это **не alpha**: alpha по `H2-G03` требует ещё Windows и импорт
данных. Сборка здесь нужна ровно для того, чтобы аудит проводился на работающем
приложении, а не на макетах.

Порядок внутри фазы обязателен: сборка, аудит, правки, и только потом тесты экранов.
Скриншотные тесты, снятые до правок, зафиксируют интерфейс, который вы собираетесь
менять, и их придётся перезаписывать целиком.

**H2-E07 — Android-сборка для аудита.** Предпосылки: `H2-E06`.
Артефакт из CI, отладочный. Локальные сборки запрещены (§10).
Границы: это не alpha и не релиз-кандидат; версионирование и подпись здесь не темы.
Готовность: APK скачивается из CI и устанавливается.

**H2-UX01 — предметный аудит интерфейса.** Предпосылки: `H2-E07`.
Проводит тимлид вместе с владельцем; исполнителю не выдаётся. Аудит не про
соответствие MD3 — это проверено в `H2-E02`. Здесь проверяется польза.

Оси аудита, по каждой — findings со степенью важности:
  1. пользовательские задачи, а не экраны: установить и подключиться; сменить сервер;
     понять, почему не работает; ограничить набор приложений; уехать в роуминг.
     Для каждой — число шагов и число переключений экранов;
  2. первый запуск: сколько шагов от установки до идущего трафика;
  3. неоднозначность настроек: две настройки, влияющие на одно; настройка, чьё имя не
     говорит о следствии; настройка, выключение которой ничего не меняет; настройка,
     требующая перезапуска туннеля, без предупреждения об этом;
  4. обратная связь об отказе: различает ли интерфейс «нет сети», «сервер не
     отвечает», «подписка истекла», «конфиг неверен» — и предлагает ли действие;
  5. опасные и необратимые действия: удаление подписки, смена режима при активном
     туннеле, импорт, перезаписывающий существующее;
  6. состояния каждого экрана: пусто, загрузка, ошибка, частичный успех;
  7. избыточная сложность: настройки, нужные единицам, — кандидаты в раздел для
     продвинутых либо на удаление;
  8. терминология: одно понятие — одно слово во всём приложении. Профиль против
     подписки, сервер против прокси против outbound против узла;
  9. согласованность с рантаймом: показывает ли интерфейс ровно то, что в снимке,
     включая период до READY, где DNS теперь отказывает быстро (§12);
  10. доступность: контраст, размер цели нажатия, экранный ридер, уменьшение анимации.

Готовность: список findings в §11, у каждого — либо задача, либо записанный отказ с
причиной. Findings без решения не остаётся.

**H2-E08 — правки по аудиту.** Предпосылки: `H2-UX01`.
Границы: scope — ровно принятые findings из `H2-UX01`, ни пунктом больше. Инвентарь
экранов может измениться только решением, записанным в `H2-UX01`.
Готовность: каждый принятый finding закрыт либо перенесён с записью в §11.

**H2-E09 — тесты экранов.** Предпосылки: `H2-E08`.
UI-тесты и скриншотные тесты на Android и desktop. Скриншоты снимаются в обоих
режимах возможностей темы (§6, `H2-E03`), иначе деградация на desktop не покрыта.
Границы: тесты снимаются после правок, а не до.
Готовность: каждый экран инвентаря покрыт UI-тестом на состояния «пусто, загрузка,
ошибка, обычное»; скриншоты существуют в обоих режимах; расхождение скриншота роняет
CI. Это M5b.

### Фаза G — Паритет, миграция, alpha → M7

**H2-G01 — импорт данных 1.x.** Предпосылки: `H2-D04`, `H2-D01`.
Подписки и настройки пользователей 1.x лежат в Hive. Новое хранилище обязано их

Границы: тест на реальном дампе Hive, не на синтетическом; импорт не меняет форму новой

Готовность: подписанные артефакты Android и Windows из CI.

**H2-G04 — кампания валидации.** Предпосылки: `H2-G03`.

sleep/wake, восстановление сети, сплит-туннель во всех режимах, proxy-only, плитка и
нотификация. Отдельным пунктом — время от старта до первого успешного соединения:
после `HC-RW-008` дозвон при нуле активных линий отказывает сразу, и надо убедиться,
что приложения ретраятся, а не остаются в отказе.
Границы: процедуру выдаёт тимлид одним куском; исполнитель её не сочиняет.
Готовность: по каждому пункту зафиксирован результат; дефекты заведены задачами. Это M7.

## 8. Критерии перехода

- A → B: оба таргета собираются; запрещённый импорт §4.9 ломает сборку; CI зелёный;
  контракт существует и порог готовности в нём один.
- B → C: контрактный тест wire-схемы зелёный; stub помечен временным; host-side
  критерий `H2-B04` выполнен. Приёмка `H2-B04-ACC` блокирует только `H2-C04`, а не
  вход в фазу C: `C01`, `C02`, `C03` и `C05` от неё не зависят.
- C → D: двадцать инвариантов зелёные; `reduce` доказанно чист; дедлайны проверены
  виртуальным временем; stub удалён и grep по нему пуст.
- D → G: каждая подсистема закрыта вертикальным срезом; ни одного перенесённого теста в
  красном; §11 содержит полное соответствие тестовых файлов и список непереносимых с
  причинами; туннель поднимается на сгенерированном конфиге.
- E → E2: аудит MD3 не ниже 7 по каждой категории; матрица expressive на desktop
  зафиксирована; каждый экран корректен в трёх классах ширины; ни один экран не имеет
  собственной фазы.
- E2 → G: каждый finding аудита имеет решение; принятые внесены; экраны покрыты
  UI- и скриншотными тестами в обоих режимах возможностей.
- F → G: контрактный тест зелёный поверх named pipe; туннель на Windows поднимается тем
  же ядром; инсталлятор подписан.
- G → релиз: импорт 1.x читает реальный дамп; чеклист паритета закрыт; `H2-G04`
  проведена и её дефекты заведены задачами.

- `libbox.aar` в git не коммитится никогда; `add -f` по нему запрещён.
- Локальные сборки APK и инсталляторов не делаются; только CI. Изъятие: alpha
  `2.0.0-alpha1` собрана локально по прямому указанию владельца, потому что CI для
  репозитория 2.0 ещё не заведён; запись — в §11. Правило остаётся в силе для всех
  последующих артефактов.
- Секреты — только через типы §4.6.
- `git add -A` и `git commit -a` запрещены; force-push запрещён.
- Ветки экспериментов не мержатся в основную.
- Версии контракта HydraCore не меняются; расширения только аддитивные (R14).
- Ничего не удаляется «по пути»: мёртвый код вне границ задачи — строкой в отчёт.
- Значения дедлайнов и порог готовности не меняются без решения тимлида.

## 11. Evidence

Заполняют исполнители. Форма: `### <ID> — <дата> — <исполнитель>`, затем `EVIDENCE`
списком фактов, затем `CONSEQUENCE` одной фразой. Только агрегированные величины и
структурные факты. Ни доменных имён, ни адресов, ни фрагментов сырых логов, ни
креденшелов.

### H2-D01 — 2026-09-01 — Codex

EVIDENCE:

- SQLDelight-схема и два пронумерованных шага миграции лежат в `:core:storage`; `check` зависит от проверки цепочки миграций;
- `secure_hive_storage_test.dart` перенесён как `core/storage/src/jvmTest/kotlin/io/hydrabox/core/storage/StorageTest.kt`: проверяются переход предыдущей схемы, отсутствие открытого текста в базе и невозможность расшифрования без провайдера;
- `secure_hive_migration_test.dart` не переносился: это импорт legacy Hive-боксов, который карточка относит к `H2-G01`.

CONSEQUENCE: настройки и будущие подписки используют единый версионированный SQLDelight-движок; ключи платформенно защищены Keystore/DPAPI.

### H2-D02 — 2026-09-01 — Codex

EVIDENCE:

- корпус `app_settings_store_test.dart` перенесён в `:core:settings`: дефолты, миграции производительности и MTU, DNS, split-routing, legal/notification/TLS и сортировка прокси проверяются на JVM;
- `SettingsStore` читает и записывает только SQLDelight-таблицу `settings`; отдельного key-value-движка нет;
- пароль прокси — `Secret`: при сохранении он зашифрован полевым кодеком и отсутствует в safe export.

CONSEQUENCE: UI и генератор конфигурации получают нормализованные настройки из единственного транзакционного хранилища.

### H2-D03 — 2026-09-01 — Codex

EVIDENCE:

- `call_vk_parasite_schema_test.dart` перенесён в `:core:subscription`; проверяются допустимые worker-пулы, четыре уникальные join-ссылки, границы таймаута и legacy `joiner`;
- учётные поля и join-ссылки становятся `Secret` непосредственно на границе схемы.

CONSEQUENCE: последующий разбор подписок получает типизированный outbound без строкового рендеринга секретов.

### H2-D04 — 2026-09-01 — Codex

EVIDENCE:

CONSEQUENCE: данные подписок сохраняются атомарно в едином хранилище и не попадают в диагностику открытым текстом.

CONSEQUENCE: генератор конфига не читает маршрутные файлы сам и остаётся детерминированным.

### ANDROID-ALPHA — 2026-09-01 — тимлид

EVIDENCE:

- Цель владельца: довести Android-фронт до собираемой alpha и запушить в ветку `hb2`.
  Windows и iOS в цель не входили.
- Артефакт: `platform/android/build/outputs/apk/debug/android-debug.apk`,
  113 881 891 байт, только `arm64-v8a`, `versionCode` 200, `versionName`
  `2.0.0-alpha1`. Отладочная подпись.
- `ciCheck` зелёный: проверка границ `commonMain`, запрет зависимости
  `:core:* -> :platform:*`, `:core:model` без зависимостей, негативный тест
  компиляции на утечку секрета (он обязан не компилироваться и не компилируется).
- Что работает по-настоящему: чистый редьюсер и двадцать инвариантов; дедлайны на
  виртуальном времени; транспорт контракта поверх binder с wire-схемой; интеграция
  ядра и подъём TUN через `VpnService`; генерация конфига из share-ссылок с учётом
  TLS, SNI, ALPN, reality, ws/grpc/http-транспорта и flow; SQLDelight с полевым
  шифрованием на ключе Keystore; добавление, список и удаление подписок; выбор
  прокси; настройки DNS, MTU и нотификации с записью в хранилище; экран диагностики;
  адаптивная навигация в трёх классах ширины; тема MD3 на брендовом seed.
- Чего в alpha нет, честным списком: счётчики трафика ядро ещё не публикует
  (`H2-C06` частично — поле в проекции есть, источника нет); задержки url-test;
  импорт подписки из QR и из файла; действия экспорта и импорта резервной копии
  (есть только read-модель); модуль обновлений (только read-модель);
  выбор приложений для сплит-туннеля (показывается только счётчик); аудит MD3
  формально не прогонялся; матрица expressive на desktop не снималась.
- Устройственная приёмка не проводилась: устройства и AVD в этой сессии не было.
  Поэтому фраза «alpha собирается и устанавливается» верна, а «туннель поднимает
  трафик» не подтверждена. Проверка — `H2-B04-ACC` и `H2-G04`.

CONSEQUENCE: Android-фронт доведён до собираемой alpha; следующий шаг — приёмка на
устройстве, затем `H2-C06` и остаток фазы E2.

## 12. Реестр решений

Приняты; переспрашивать не нужно, отменяет только тимлид.

| Решение | Основание |
|---|---|
| `GATE §W` и soak в 1.x не проводятся; reference snapshot не является валидированным baseline. | Решение владельца. 1.x — донор, а не релизная ветка; скрытые дефекты ищутся на alpha 2.0. |
| iOS не входит в initial release ни реализацией, ни feasibility validation; общий код не должен препятствовать добавлению `iosMain`. | Решение владельца. Требование живёт в §4.9 как машинная проверка. |
| Перенос логики идёт вертикальными срезами по подсистемам. | Предварительный перенос всего тестового корпуса даёт тысячи красных тестов и ни одной работающей подсистемы. |
| Порядок подсистем в фазе D задан зависимостями донора: генерация конфига последняя. | `singbox_config_builder` импортирует модели и парсеры подписок и хранилище настроек; `outbound_schema` используется разбором подписок. |
| Ходячий скелет (фаза B) идёт до настоящего ядра, ценой временного stub. | Снимает риск биндинга, процессной границы и wire-схемы до того, как на них построены логика и интерфейс. |
| Эффекты — данные; ядро ничего не исполняет. | В 1.x решение и исполнение жили в одном классе, и поведение нельзя было проверить без запуска сервиса. |
| Время — переданное значение, не источник. | Тесты на дедлайны иначе требуют реального ожидания. |
| Секреты защищены типами, а не санитайзером на выходе. | Барьер, о котором можно забыть, забывают. |
| Исход команды выводится из снимка с дедлайном, не корреляцией по `commandId`. | Корреляция по идентификатору создала бы второй источник истины о состоянии. |
| Пять генераций — пять типов, а не `Int`. | В 1.x путаница между `commandGeneration` и `networkGeneration` потребовала поправки к плану. |
| `NETWORK_CHANGED` не инкрементирует `commandGeneration`. | Смена сети не вытесняет намерение пользователя; устаревание сетевых событий обслуживает `networkGeneration`. |
| Единственный триггер восстановления — `device_idle_exit`, только Android. | Эксперимент E7 закрыт по P2: три остальных триггера не нужны. |
| Подмена маршрута DNS на direct или local до READY запрещена. | Любой успешный ответ до READY идёт вне туннеля, то есть отдаёт провайдеру список доменов на каждом старте. До READY DNS обязан отказывать. |
| Отказ дозвона при нуле активных линий — немедленный. | Ожидание до `WorkerConnectTimeout` выглядит для приложения обрывом сети; быстрый отказ вызывает ретрай. |
| `default_domain_resolver = dns-local`; `domain_resolver: dns-local` для DNS-сервера с не-IP адресом. | DNS-сервер не может разрешать собственное имя через маршрут, который сам обслуживает. |
| Базовая пригодная сеть исключает `TRANSPORT_VPN`. | Иначе собственный туннель считается пригодным апстримом. |
| Интерфейс доводится до ядра в пути replay при регистрации слушателя. | Иначе первый холодный старт не завершается. |
| Порог готовности транспорта существует в одном месте контракта. | В 1.x расхождение «процесс жив» против «транспорт готов» давало ложный READY. |
| Подсистема probe не вводится заново. | Давала второй источник истины и могла задерживать `STOP`. |
| Persisted state описывает только желаемую конфигурацию. | Файл, утверждающий что что-то живо, расходится с реальностью при смерти процесса. |
| Двухпроцессная модель на Android сохраняется. | Отделяет UI от VpnService; граница остаётся, но становится Kotlin↔Kotlin и типизированной. |
| У каждой read-модели ровно один владелец-производитель; проекция только соединяет и ничего не производит. | Иначе одна величина начинает выводиться в двух местах и расходиться — именно так в 1.x UI показывал не то, что рантайм. Таблица владельцев в §4.5 нормативна. |
| Живая часть каталога (группы, выбор, задержки) принадлежит рантайму, настроенная (outbound'ы, цепочки) — подпискам; встречаются они только в проекции. | Это две разные истины: одна о том, что описано, другая о том, что сообщает ядро. В 1.x они смешивались в нескольких местах. |
| Любая операция вне рантайма описывается общим `OperationState` из `:core:model`. | Пять похожих, но разных перечислений превращают проекцию в набор адаптеров. |
| Обновления приложения получают собственный модуль `:core:update`. | В 1.x это был сервис на 42 КБ без владельца; вынос оставляет `:core:settings` моделью, а не сервисом. |
| Один контрактный тест wire-схемы обслуживает binder и named pipe. | Это и есть проверка того, что граница одна, а не две похожие. |
| Аудит пользы интерфейса проводится на работающей Android-сборке между фазами E и G, и тесты экранов снимаются после его правок, а не до. | Аудит по макетам находит другое и меньше. Скриншотные тесты, снятые до правок, фиксируют интерфейс, который предстоит менять, и переписываются целиком — это чистая потеря. |
| Приёмки вех M2 и M6 проводятся на устройстве, в изъятие из правила «никаких устройственных проверок до фазы G». | Веха «туннель поднимается» иначе недоказуема, а недоказанная веха обесценивает раннее снятие риска, ради которого фаза B стоит второй. Обе приёмки ограничены фиксированным коротким чеклистом и не являются soak. |

| Движок хранилища — SQLDelight, единственный на все данные, включая настройки. | Четыре причины, в порядке весомости. Многопроцессный доступ: на Android состояние делят UI-процесс и `:core`, на Windows — GUI и helper-сервис; SQLite это выдерживает блокировками, документный файл с двумя писателями — нет. Частичная запись: сохранение одной подписки не перезаписывает весь набор, а значит убийство процесса посередине не портит остальное. Транзакции дают атомарность, которую иначе пришлось бы воспроизводить руками и хуже. Цепочка миграций проверяется инструментом, а не глазами. Apple-таргеты поддержаны, поэтому §4.9 не нарушается. |
| Настройки не получают отдельного движка. | Два движка — две механики миграции, которые расходятся; выигрыш от key-value для нескольких десятков ключей этого не стоит. |
| Секреты шифруются на уровне поля, а не всей базы, ключ — через `expect`/`actual` провайдер. | Шифрование всей базы требует SQLCipher на Android и не имеет чистого аналога на desktop. Полевое шифрование единообразно на всех платформах и совпадает по границе с секретными типами §4.6. Оговорка: без аппаратной привязки ключа шифрование на desktop даёт немного, поэтому провайдер обязан использовать Keystore на Android и DPAPI на Windows, а не самодельный ключ рядом с базой. |

| Деградация на desktop: возможности разрешаются один раз в теме, экраны о платформе не знают; наименьший общий знаменатель применяется поштучно. | Главный риск здесь не выбор облика, а расхождение: два визуальных языка расходятся, а экраны обрастают ветвлениями по платформе. Ветвление обязано существовать ровно в одном месте, и это тема. Компонент без равнороллевого аналога исключается целиком, иначе на Windows появится собственная вёрстка. |
| Пиксельный паритет между Android и desktop не является целью; эталон визуальной проработки — Android. | Погоня за одинаковостью на Windows съедает недели и противоречит адаптивности, ради которой MD3 и берут. Требование к desktop — корректность и спокойствие. |

Ожидают принятия: Panama против JNA (`H2-F02`).

## 15. Как выдавать задачи

`docs/HYDRABOX2_DISPATCH.md`. Наряд писать не нужно: карточка в §6, правила поведения в

тимлид — это значит, что в карточке дефект либо развилка, зарезервированная за ним.
